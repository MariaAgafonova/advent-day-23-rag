# Document Indexer · Реранкинг

## Быстрый сценарий

Откройте <http://localhost:8503> → **Реранкинг**. Этот экран открывается по умолчанию.

1. Выберите **«Фильтр»** или **«Реранкер»**, введите вопрос.
2. Настройте **Top-K до обработки — 15**, **Top-K после обработки — 5**.
3. В режиме «Фильтр» задайте cosine-порог (стартовый **0.85**, не оптимум).
   В режиме «Реранкер» отсечение по score по умолчанию выключено; при необходимости
   включите отдельный ручной порог raw score.
4. Нажмите **«Сравнить ответы»**. Слева ответ без обработки, справа с выбранной обработкой.

| Режим | Что делает | Порог |
|---|---|---|
| Фильтр | Отбрасывает cosine score ниже порога, сохраняет исходный порядок | Cosine similarity, −1…1 |
| Реранкер | Отдельная cross-encoder модель оценивает пары вопрос–чанк, сортирует по новому score и берёт final_k | Необязательный raw logit, отдельная шкала |

Rewrite выключен в обоих ответах. Индекс, генеративная модель, retrieval_k, final_k
и контекстный бюджет одинаковы. Ручная калибровка **не нужна для этого сравнения**.

Под ответами видно число отсеянных фрагментов. Источники, кандидаты, предыдущие сравнения
и экспорт свёрнуты, пока они не нужны. В «Оценить качество ответов» можно сохранить
свой выбор и комментарий; генерация при этом повторно не вызывается.

## Отдельная модель реранкинга

Используется [cross-encoder/mmarco-mMiniLMv2-L12-H384-v1](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1)
с поддержкой русского и английского языков. Закреплённая revision:
`1427fd652930e4ba29e8149678df786c240d8825`. Модель запускается локально на **CPU**,
веса и tokenizer занимают примерно 490 МБ; после скачивания используется локальный кеш.

В соответствии с [конфигурацией модели](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1/blob/1427fd652930e4ba29e8149678df786c240d8825/config.json)
используются исходные **logits / Identity**. Sigmoid не применяется, score не объявляется
вероятностью. Cosine-порог 0.85 не переносится на эту шкалу. Откалиброванного порога
реранкера пока нет, поэтому по умолчанию выполняется только пересортировка и выбор Top-K.

Реранкер получает **исходный вопрос**, в том числе при вызове из расширенного rewrite-pipeline.
При равных scores сохраняется исходный retrieval rank. Для каждого кандидата сохраняются
оба scores, оба ранга, прохождение порога и причина исключения. Они видны в «Чанки: scores,
порядок и отсечение» и в экспорте. История в простом экране разделена по выбранному режиму.

Лимит пары — **512 токенов**. Вопрос не обрезается; если пара длиннее, обрезается только
хвост текста чанка. Сохраняются `reranker_input_tokens`, `reranker_used_tokens`,
`reranker_truncated`; UI показывает предупреждение. Исходный текст чанка в индексе
сохраняется. Слишком длинный вопрос или ошибка модели — техническая ошибка этапа
`reranker`, без скрытого возврата к baseline и без подмены отсутствием контекста.

CLI с тем же pipeline:

```powershell
.\.venv\Scripts\python.exe -m document_indexer ask --mode filter --index output/structural.sqlite --question "Как сохранить UI state после смерти процесса?" --threshold 0.85
.\.venv\Scripts\python.exe -m document_indexer ask --mode reranker --index output/structural.sqlite --question "Как сохранить UI state после смерти процесса?" --retrieval-k 15 --final-k 5
# Отдельный ручной raw-score порог (пример, не откалиброванное значение):
.\.venv\Scripts\python.exe -m document_indexer ask --mode reranker --index output/structural.sqlite --question "Как сохранить UI state?" --reranker-threshold -3
```

Модель и revision задаются `--reranker-model` и `--reranker-revision`, лимит —
`--reranker-max-length`. Revision обязана быть точным commit hash. Калибровка cosine
не принимается для реранкера. Новых Python-зависимостей не требуется: используются
уже установленные Transformers, PyTorch и safetensors.

Проверка модели отдельно от unit-тестов:

```powershell
.\.venv\Scripts\python.exe -m pytest -m integration tests/test_reranker_integration.py -q
# Явное сравнение с baseline на 3 вопросах, до 6 генераций:
.\.venv\Scripts\python.exe scripts/verify_reranker.py --live
```

Прежние четыре режима и подробная калибровка доступны по переключателю
**«Расширенный режим: rewrite и калибровка»**. Описанный ниже основной эксперимент
на 10 вопросах относится именно к расширенному режиму.

## Что изменилось

| Режим | Поиск | Обработка кандидатов | Вопрос генерации |
|---|---|---|---|
| Baseline | Исходный вопрос | Первые final_k | Исходный |
| Rewrite | Переписанный запрос | Первые final_k | Исходный |
| Filter | Исходный вопрос | Cosine-порог, затем final_k | Исходный |
| Rewrite + Filter | Переписанный запрос | Cosine-порог, затем final_k | Исходный |

`retrieval_k=15`, `final_k=5` — стартовые значения, не найденный оптимум.
Требуется `0 < final_k <= retrieval_k`. Во всех режимах одного эксперимента одинаковы индекс,
модели, параметры генерации, бюджет контекста, оба k и контрольные вопросы.
Промпт ответа остаётся `day22-v1`. No-rag не входит в основной эксперимент Дня 23.

**Фильтрация, а не реранкинг:** `similarity_threshold` сохраняет чанки с
`retrieval_score >= threshold`, не меняя порядок. Score — cosine similarity, не вероятность
правильного ответа. Отдельный cross-encoder реализован в режиме **Реранкер**, описанном выше.
Пороги разных типов не смешиваются.

**Rewrite:** существующий LLMClient получает только исходный вопрос и отдельный промпт
`day23-rewrite-v1`; один вызов, температура 0, максимум 512 выходных токенов (не больше общего лимита).
Ответ — JSON `{"rewritten_query":"..."}`. Проверяются структура, непустая строка, 2000 символов
и лимит embedding-токенизатора. При ошибке используется исходный вопрос с явным статусом
`fallback` и причиной. Сохранение смысла проверяет человек, техническая валидация этого не гарантирует.
Эталоны, ожидаемые источники и найденные чанки в rewrite не передаются.

Для кандидатов сохраняются исходные rank/score, прохождение порога, выбор в final_k,
включение в контекст и цитирование. Причины исключения: `below_threshold`, `final_k_limit`,
`duplicate_text`, `covered_range`, `context_budget`. Номера S1… назначаются только после отбора
контекста; отсеянные чанки не доступны для цитирования. Счётчик включённых чанков использует
уникальные chunk ID: один чанк иногда даёт несколько неперекрывающихся фрагментов.

Когда всё отсеяно: **«После фильтрации подходящие фрагменты не найдены»**,
статус `no_relevant_context`, `generation_skipped=true`. Генерация не вызывается, скрытого
возврата к baseline/no-rag нет. `no_results`, `empty_context` и технические ошибки этапов различаются.

## Калибровка: требуется ваша ручная разметка

Численное значение калиброванного порога пока **не выбрано**. Одиночные ручные запросы
доступны с явно введённым порогом и пометкой «Порог не откалиброван».
Основной эксперимент заблокирован до завершения разметки человеком.

1. Откройте **Реранкинг → Расширенный режим → Калибровка**. Выберите уже подготовленный набор пар;
   «Подготовить calibration-пары» создаёт новый набор и делает до 8 rewrite-вызовов.
2. Набор `data/day23_calibration_questions.json` содержит 8 дополнительных вопросов:
   четыре перефразированных запроса, две близкие отсутствующие темы, два вопроса без ответа.
   Пересечения ID/нормализованных текстов с 10 test-вопросами запрещены.
3. Для каждого исходного вопроса ищутся кандидаты по исходной и переписанной формулировкам.
   Одинаковая пара вопрос–чанк размечается один раз; оба наблюдения scores сохраняются.
4. Прочитайте вопрос и текст, выберите «Релевантный», «Частично релевантный» или
   «Нерелевантный», подтвердите проверку и сохраните. Автоматических семантических меток нет.
5. Нажмите **Рассчитать и зафиксировать порог**. Требуется полная разметка,
   включая положительные и отрицательные примеры. Частично релевантные считаются
   **отрицательными** для расчётов; исходная метка сохраняется.
6. Перебираются наблюдаемые scores и граничные −1/1; выводятся precision, recall, F1,
   доля запросов без контекста, отдельно original/rewrite и вместе. Единица расчёта —
   наблюдение query–chunk; общий кандидат может иметь два scores, но одну ручную метку.
7. Правило выбора: **максимальный F1 → больший recall → меньший порог**.
   Recall относится к найденным кандидатам, не ко всем релевантным фрагментам корпуса.
8. Выберите сохранённую калибровку в настройках. Порог, таблица, правило, версия набора,
   снимок меток, индекс, embedding revision, rewrite-модель и параметры фиксируются.
   Несовместимые настройки не получают статус откалиброванных.

Нельзя настраивать порог по ответам на 10 основных вопросов. Малый calibration-набор
даёт только предварительные выводы; перенос на другую модель или тип score запрещён.

## Эксперимент, оценка и отчёт

После ручной калибровки **Реранкинг → Расширенный режим → Эксперимент → Запустить 4 режима на 10 вопросах**
или команда `evaluate-day23` создаёт 40 результатов: до 40 генераций + 10 rewrite-вызовов.
Одна формулировка, включая fallback, повторно используется в обоих rewrite-режимах.
Её ID и provenance сохраняются; общий usage учитывает вызов один раз. Временные HTTP-ошибки
могут вызвать повтор запроса — число попыток выводится отдельно от логических вызовов.

Оцените ответы в интерфейсе по рубрике Дня 22: корректность 0–2, факты/полнота,
неподтверждённые утверждения, цитирования, недостаток информации и ложные предпосылки.
Для rewrite отметьте сохранение смысла и улучшение/ухудшение поиска; для вопросов без
ответа — оставшийся нерелевантный контекст. Непроверенные ответы не входят в средние.
Автоматическая проверка диапазонов отслеживает доказательства до фильтра, после него,
в final_k и в фактическом контексте; false rejection виден отдельно. Это не смысловой судья.

JSON, CSV и Markdown содержат настройки, кандидатов, причины исключения, точный контекст,
ответы, ссылки, ошибки, ручные оценки, время rewrite/retrieval/filter/context/generation,
раздельный usage rewrite/generation. Неизвестный usage отмечается, не выдаётся за ноль.
Таблица сопоставляет четыре режима. Разбор улучшения, ухудшения/отсутствия улучшения
и недостаточной информации строится по проверенным ответам; при отсутствии данных
соответствующий вывод явно недоступен.

Данные Дня 23: `output/day23_experiments/experiments.sqlite`; файлы экспорта:
`output/day23_experiments/<run_id>.json/.csv/.md`. Архив Дня 22 находится отдельно в
`output/rag_experiments`. Просмотр сохранённого run не зависит от доступности LLM.

## Настройки LLM

```powershell
Copy-Item .env.example .env
notepad .env
```

| Переменная | Назначение |
|---|---|
| `LLM_API_KEY` | Ключ провайдера; в примере пустой |
| `LLM_BASE_URL` | Корневой URL API, обычно с `/v1`; клиент добавляет `/chat/completions` |
| `LLM_MODEL` | Точный ID доступной вам модели; значения по умолчанию нет |
| `LLM_TEMPERATURE` | Общая температура, по умолчанию `0.2` |
| `LLM_MAX_OUTPUT_TOKENS` | Общий предел ответа и отдельный резерв, `512` |
| `LLM_TIMEOUT_SECONDS` | Таймаут HTTP-запроса, `60` |
| `LLM_CONTEXT_WINDOW_TOKENS` | Окно модели; проверьте по документации провайдера, стартовое ограничение `8192` |
| `RAG_MAX_CONTEXT_TOKENS` | Бюджет контекста с метаданными, `3000` |
| `LLM_OUTPUT_TOKEN_PARAMETER` | `max_tokens` или `max_completion_tokens`, согласно API выбранной модели |
| `LLM_THINKING` | Необязательное расширение провайдера: `enabled` / `disabled`; по умолчанию не отправляется |

Для DeepSeek можно напрямую использовать `DEEPSEEK_API_KEY`, `DEEPSEEK_BASE_URL`, `DEEPSEEK_MODEL`, `DEEPSEEK_TIMEOUT_SECONDS`, `DEEPSEEK_MAX_TOKENS`, `DEEPSEEK_THINKING`. В пределах одного источника настроек `LLM_*` имеет приоритет над соответствующим алиасом; переменные процесса имеют приоритет над файлом. `DEEPSEEK_THINKING=disabled` отправляется как `thinking: {"type": "disabled"}`. `WEB_PORT` и `WEB_SECRET_KEY` относятся к другому веб-стеку: Streamlit запускается с `--server.port`, ключ сессии этого типа ему не нужен.

Переменные процесса имеют приоритет над `.env`. Файл читается только в корне проекта, без поиска ключей в соседних заданиях; интерполяция отключена. Ключ не попадает в SQLite, prompt, UI, логи и отчёты. `.env` исключён из Git. Ошибки HTTP сохраняются безопасным кодом без сырого тела ответа или заголовков.

Адаптер реализует OpenAI-совместимый [Chat Completions API](https://developers.openai.com/api/reference/resources/chat) через абстракцию `LLMClient`. Модель должна поддерживать `messages`, `temperature` и выбранный параметр лимита выхода. Несовместимость вызывает явную ошибку; скрытой смены модели или параметров нет. Поддерживается текстовый ответ, usage и finish_reason.

Один повтор разрешён при таймауте/ошибке подключения и HTTP 408/429/500/502/503/504. Ошибки 400/401/403/404 не повторяются. Редиректы отключены, удалённый API требует HTTPS. Записываются логические вызовы и число фактических попыток. При неизвестном тарифе выводятся usage и «Стоимость не рассчитана».

## Режимы, prompt и контекст

**Без RAG:** общая инструкция + вопрос → LLM. В prompt нет документов, названий файлов, retrieval, эталонов или истории. `retrieved_chunks` и `context_items` пустые, `index_version=null`.

**С RAG:** вопрос → E5 → поиск → отбор контекста → LLM → проверка ссылок → сохранение. В обоих режимах одинаковые провайдер, модель, вопрос, температура и максимальная длина ответа. История не передаётся.

`ContextBuilder` сохраняет порядок релевантности, удаляет точные дубликаты и уже включённые диапазоны одного документа. Каждый включённый фрагмент сохраняет связь с chunk ID, хешем документа и исходными координатами `[start,end)`. Обрезка имеет `truncated=true`; строки/страницы пересчитываются по фактическому диапазону. В бюджет включены метаданные и обрамление prompt, выход резервируется отдельно. Универсального порога similarity нет.

Embedding-токенизатор не используется для LLM. Если модель распознана `tiktoken`, применяется её текстовая токенизация с консервативной надбавкой на chat framing. Иначе используется **явно обозначенная оценка: один UTF-8 байт на бюджетную единицу, не точное число токенов LLM**. Она может существенно сокращать контекст. Достоверное usage возвращает провайдер.

Формат фрагмента: `[S1]`, Title, Source, Section, Location, Text. Контекст JSON-экранирован между `BEGIN_UNTRUSTED_CONTEXT_JSON` / `END_UNTRUSTED_CONTEXT_JSON`, вопрос отделён. Версия prompt — `day22-v1`. Общие правила: русский краткий ответ, без выдуманных фактов, с обозначением неопределённости. RAG дополнительно требует опоры на фрагменты, игнорирования команд в документах и ссылок только на существующие ID. При нехватке сведений нужно говорить о недостаточности предоставленных фрагментов, не всей базы. Пустой контекст обозначается явно. Внутренняя цепочка рассуждений не запрашивается.

## Интерфейс

Сохранены экраны «Документы», «Индексация», «Чанки», «Поиск», «Сравнение».

**«RAG-запрос»**: многострочный вопрос, режим, готовый индекс, top-k, общие настройки. Сравнение показывает no-RAG слева и RAG справа, статус, ошибку, время и usage каждого ответа. Отдельно показаны Retrieved (найдено), Included (передано модели), Cited (процитировано). Кнопка `[S1]` под ответом открывает сохранённый источник и выделяет переданный диапазон. Неизвестные ссылки помечаются ошибкой, не переназначаются; повторные ссылки дедуплицируются.

**«Оценка RAG»**: 10 вопросов и ожидания, явная кнопка запуска 20 вызовов, реальный счётчик, результаты, доказательства и ручная рубрика. Нет платных запросов при открытии, переключении экранов или чтении старого результата. JobManager работает в фоне и не допускает второй активный job с тем же ключом. Рабочий поток не вызывает Streamlit.

Валидность ссылки не доказывает поддержку утверждения источником. Это проверяется вручную. Similarity не является вероятностью правильности ответа.

## Хранение и экспорт

### Просмотр запросов к API

В «RAG-запрос» после сравнения откройте **«Сравнить запросы к API»**: оба запроса показаны рядом, таблица отмечает совпадение параметров, вкладка **«Различия»** выделяет добавленные правила и RAG-контекст. Каждый запрос можно прочитать по сообщениям system/user, посмотреть полным JSON или скачать. Этот же просмотр доступен при разборе контрольного вопроса на экране «Оценка RAG»; у одиночного ответа есть блок **«Запрос к API»**.

Для новых вызовов сохраняется снимок фактически отправленного тела из адаптера: метод, URL, timeout и JSON body, включая model, messages, temperature, лимит выхода и thinking. Authorization и API-ключ не сохраняются. Снимок остаётся прежним после изменения `.env`, доступен и при ошибке провайдера. Просмотр не вызывает генерацию. Для старых экспериментов без снимка явно показываются только записанные сообщения и известные параметры; недостающие URL и поля не подставляются из текущей конфигурации.

`output/rag_experiments/experiments.sqlite`: `runs` — запуск/время/настройки, `answers` — отдельные ответы с prompt, retrieval, контекстом, ссылками, usage и ошибками, `snapshots` — нормализованные документы выбранной версии, `reviews` — ручные оценки. Каждый запуск получает новый UUID; каждый ответ сохраняется сразу. Ошибка второго режима не удаляет первый.

Снимок источника доступен после изменения документов или индекса. Открытие эксперимента не обращается к LLM. При остановке сервера уже записанные ответы сохраняются; отсутствующие результаты не выдаются за успешные. Автоматического возобновления незавершённых вызовов нет.

JSON экспортирует полный результат и снимок, CSV — сводку ответов, Markdown — ответы, ошибки, оценки и выводы. Файлы именуются по `run_id`. Кнопки скачивания используют актуальные сохранённые ручные оценки. Ключ не сохраняется; полный prompt сохраняется локально.

## Разметка и ручная оценка

`data/rag_questions.json` подготовлен **до генерации**: 4 фактических вопроса, 2 перефразирования, 2 составных, 1 с ложной предпосылкой, 1 с недостатком сведений. `scripts/prepare_rag_questions.py` содержит вручную выбранные формулировки и anchors абзацев; не использует поиск или LLM.

Вопрос содержит `id`, `question`, `category`, `answerable_from_corpus`, `expected_behavior`, взвешенные `expected_facts`, `forbidden_claims`, `expected_sources`. Каждый источник — `source`, `document_hash`, `start_char`, `end_char`, `evidence_excerpt`. Хеш и точный диапазон нормализованного текста проверяются. Chunk ID в эталонах не используется. Для вопроса без ответа источники могут быть пустыми. Эталоны не передаются модели. После изменения корпуса разметку нужно проверить заново, не подгоняя под результаты поиска.

- Корректность: 0 — неверно/существенное противоречие; 1 — частично/неполно; 2 — правильно без существенных ошибок.
- Полнота: сумма весов отмеченных фактов / общий вес. Если фактов нет — N/A.
- Отдельно считаются существенные противоречия эталону и, для RAG, утверждения без опоры на переданный контекст.
- Автоматически проверяются найденный документ, полный доказательный диапазон в retrieval/context и цитирование. Смысловая поддержка утверждения проверяется человеком.
- Для соответствующих вопросов отмечаются распознавание недостаточности информации и отвержение ложной предпосылки.
- Источники no-RAG — N/A, не ноль. Отсутствие ответа в корпусе не означает, что no-RAG обязан его не знать.
- Только явно сохранённые `reviewed` входят в средние. `unreviewed` не учитываются; видны число проверенных ответов и полностью проверенных пар.

Ключевые слова не выдаются за проверку фактов. LLM-as-judge отсутствует. Неуспешные вызовы показываются и экспортируются отдельно от ответов.

## Демонстрация на 3–5 минут

После настройки `.env` выберите structural и «Сравнить оба»:

2. Задайте q07 о viewModelScope и WorkManager. Проверьте обе части доказательства в Retrieved и Included, откройте `[S1]`.

4. На «Оценка RAG» явно запустите 20 вызовов, разберите ошибки, сохраните ручные оценки и экспортируйте отчёт.

## Ограничения

Генерация проверена коротким реальным запросом; пакетный эксперимент на 20 вызовов и ручная оценка ещё не выполнены. Индекс сохранён без подгонки retrieval под вопросы. Неизвестный tokenizer приводит к грубой консервативной оценке бюджета. Prompt-защита от команд в документах не является формальной гарантией. Jobs живут в процессе; результаты и источники — на диске. Нет веб-поиска, MCP, инструментов агента, истории, reranking, hybrid search, автоматической индексации, OCR и автоматического смыслового судьи.
